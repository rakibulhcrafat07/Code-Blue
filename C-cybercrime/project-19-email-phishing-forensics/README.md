# Project 19 — Email Forensics & Phishing Investigation

**Status:** 🟡 Fictional training case (all evidence simulated) · to be replaced with lab-generated evidence
**Track:** Cybercrime Investigation

> ⚠️ **Fictional scenario.** Every name, domain, IP address, header and hash in this project is invented for training. Domains use the reserved `.example` / `example.com` / `example.net` names and IPs come from the documentation ranges (RFC 5737: 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24), so nothing here points to a real person or system. All values are marked *(sim)* in spirit throughout.

## Objective
Decide whether an invoice email that appears to come from the CEO is genuine, trace its real origin from the headers, evaluate SPF/DKIM/DMARC correctly, triage the attachment safely, and produce IOCs and mail-server recommendations.

## Scenario
On **Tue 12 Mar 2024 08:47 UTC**, the finance officer at *Northwind Traders* (`northwind.example`) received an email from "**David Ross (CEO)**" asking for urgent payment of an attached supplier invoice before a board meeting. The finance officer forwarded it to the security team instead of paying.

**Investigative questions**
1. Did the email really come from the CEO's mailbox?
2. Where did it actually originate?
3. Is the attachment malicious?
4. What should be blocked and what should the mail server enforce?

## Step 3 — Compare identity fields
| Field | Value | Assessment |
|---|---|---|
| From (display) | David Ross (CEO) | Matches the CEO's name |
| From (address) | `david.ross@northwind.example` | **Spoofed**: looks internal |
| Return-Path / envelope | `billing@mail-northwlnd.example` | Different domain: **northw-l-nd** (letter *l* instead of *i*) |
| Reply-To | `d.ross.ceo@freemail.example` | Replies would go to an external free-mail account |
| Message-ID domain | `mail-northwlnd.example` | Generated by the look-alike domain, not by Northwind's server |
| Control sample E3 | Envelope, DKIM and Message-ID all `northwind.example`, first hop is Northwind's own Exchange | Shows what genuine CEO mail looks like |

## Step 4 — SPF, DKIM and DMARC: what the results really mean
| Check | Result | Correct interpretation |
|---|---|---|
| SPF | pass for `mail-northwlnd.example` | The **look-alike** domain authorised its own server. SPF checks the envelope domain only, so it says nothing about the visible From |
| DKIM | pass, `d=mail-northwlnd.example` | The message was signed by the **attacker's** domain and was not altered in transit. It does not mean the email is legitimate |
| DMARC | **fail** for `northwind.example` | Neither SPF nor DKIM aligned with the visible From domain. This is the result that exposes the spoof |
| DMARC policy | `p=none` | Northwind only monitors DMARC, so the failed message was still delivered |

`dig` confirmation *(sim)*:
```
$ dig +short TXT _dmarc.northwind.example
"v=DMARC1; p=none; rua=mailto:dmarc@northwind.example"
$ dig +short TXT mail-northwlnd.example
"v=spf1 ip4:203.0.113.58 -all"
```

> **Key lesson:** "SPF/DKIM pass" never proves who sent an email. A pass only shows the sending domain controls that server or key. Always check **alignment** with the From domain (DMARC).

## Step 5 — Origin and infrastructure
| Indicator | Finding *(sim)* |
|---|---|
| `198.51.100.73` | Residential DSL address of the ISP `isp.example`; the attacker's own connection (first `Received` hop, from authenticated submission) |
| `203.0.113.58` | VPS hosting the attacker's mail server |
| `mail-northwlnd.example` | Registered 2024-03-10, two days before the email, via a privacy-protected registrar |
| Reputation | Look-alike domain listed on two public blocklists after 13 Mar |

> **Note on blocklists:** blocklist hits on large providers' internal relays (e.g. `*.prod.outlook.com`, `mx.google.com`) are common false positives in header analyzers. Only the attacker-controlled hops are meaningful.

> **Limits of attribution:** the first-hop IP identifies a connection, not a person. Linking it to an individual requires a legal request to the ISP, which is outside the analyst's role.

## Recommendations
1. Move DMARC from `p=none` → `p=quarantine` → `p=reject` after reviewing aggregate reports.
2. Add an "External sender" banner and flag display names matching executives when the domain is external.
3. Block macro-enabled Office files from external senders at the gateway.
4. Register or monitor common look-alike variants of the company domain.
5. Require out-of-band confirmation (phone call) for any payment request received by email.

## Lessons from Earlier Real-World Analyses
These mistakes from an earlier engagement (details confidential) shaped this methodology:
| Earlier mistake | Correct approach |
|---|---|
| Treated "SPF/DKIM/DMARC pass" as proof the email was authentic | Check alignment; a pass only proves domain control |
| Reported Microsoft/Google internal relays as "blacklisted" | Ignore provider infrastructure; assess attacker-controlled hops only |
| Labelled attachments "serious virus" without testing | State verdicts only from static/dynamic analysis or hash reputation |
| Wrote "no phishing" and "PDF is phishing" in the same section | One verdict per artefact, backed by evidence |
| Expected headers to reveal the sender's device | Webmail hides client IPs; attribution needs provider/ISP records |

## Key Learnings
1. DMARC alignment, not SPF or DKIM alone, determines whether the visible sender is genuine.
2. Read `Received` headers bottom-up; only the first external hop says anything about the origin.
3. Client evidence stays confidential: publish methods, not cases.
